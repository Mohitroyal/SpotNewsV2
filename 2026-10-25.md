## 2. Detailed Technical Breakdown

### 2.1 Coin Redemption System & Costing
- **Database Schema (`public.redeem_requests`)**:
  ```sql
  CREATE TABLE public.redeem_requests (
      id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
      user_id uuid REFERENCES public.profiles(id) ON DELETE CASCADE,
      user_email text,
      user_name text,
      user_phone text,
      coins_redeemed integer NOT NULL CHECK (coins_redeemed >= 500),
      amount_inr numeric(10, 2) NOT NULL,
      redeem_type text NOT NULL CHECK (redeem_type IN ('recharge', 'upi')),
      target_account text NOT NULL,
      status text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'completed', 'rejected')),
      admin_notes text,
      created_at timestamptz DEFAULT now(),
      updated_at timestamptz DEFAULT now()
  );
  ```
- **Costing and Pricing Rules**:
  - `Views`: 100 views = 1 coin
  - `Likes`: 50 likes = 1 coin
  - `Comments`: 25 comments = 2 coins
  - `Shares`: 50 shares = 5 coins
  - `Conversion`: 10 coins = ₹1
  - `Minimum Threshold`: 500 coins (= ₹50)
  - `Payout Types`: Mobile Recharge (10-digit number) and UPI (VPA address)
- **Frontend Integration**:
  - `StatsScreen.tsx` queries `redeemService.getUserDeductedCoins(user.id)` and `redeemService.fetchUserRedeems(user.id)` on load.
  - Submissions write directly to Supabase and show a real-time status card (*Pending*, *Paid*, *Refunded*).
  - Admins can review all requests in `AdminScreen` under the **💰 Redemptions** tab, approve/mark as paid, or reject with a reason (which automatically refunds coins to the reporter's available balance).

### 2.2 Feed Approval Gating (Clippings & Ads)
- **Problem**: Previously, unapproved clippings with `is_posted = true` or `status != 'pending_approval'` could leak into the public feed if not strictly validated against `status = 'approved'`.
- **Solution**:
  - `FeedScreen.tsx`: Enforced `.eq('is_posted', true).eq('status', 'approved')` across all Supabase queries (primary today's query, district fallback, and national fallback), and updated the JavaScript in-memory filter to strictly require `c.is_posted === true && c.status === 'approved'`.
  - `NewsScreen.tsx`: Gated `handlePostToFeed`. Regular reporters/users can only submit for approval (`status = 'pending_approval', is_posted = false`), notifying the district admin. Only Admins and Superadmins have direct posting permissions.
  - `daily_newspaper_views.py`: Updated Django newspaper clipping queries to enforce `c.is_posted = true AND c.status = 'approved'`.
  - `Local Ads`: Confirmed `localAdsService.fetchActiveLocalAds` strictly enforces `status = 'active'`, which requires Superadmin review and verified payment.

### 2.3 Push Notification Architecture & Bug Fixes
- **Approval Push to Reporter**:
  - In `admin.service.ts` (`approveClippingToFeed`), the system retrieves the reporter's FCM device tokens from `device_tokens` and dispatches a personalized notification:
    - Title: `🎉 మీ వార్త ఆమోదించబడింది! (Clipping Approved)`
    - Message: `మీ వార్తా కథనం జిల్లా అడ్మిన్ ద్వారా ఆమోదించబడి ఫీడ్‌లో ప్రత్యక్ష ప్రసారం చేయబడింది.`
  - In `rejectClippingSubmission`, a rejection notification with the admin's reason is sent to the reporter.
- **Broadcast Push to Readers**:
  - Broadcasts push alerts to the district and `all` topic subscribers when a clipping is approved to drive immediate traffic.
- **Backend Stability**:
  - Corrected line 275 `IndentationError` in `spotnews_django/core/services/notification_service.py`.
  - Added dynamic Firebase service account credential loading from `public.app_config` in PostgreSQL to ensure Render deployment succeeds without exposing JSON secrets to git.
